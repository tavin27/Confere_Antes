# Database Documentation

## Overview

The schema defined in `DataBase.sql` is designed for PostgreSQL. It uses PostgreSQL-specific features, including `pgcrypto`, UUID generation, `TIMESTAMPTZ`, `TEXT[]`, `JSONB`, partial indexes, and PL/pgSQL triggers. The folder also contains `INDEX.sql`, `CreateDB.py`, and `CreateCodeVerifyEntry.py`.

For a fresh, already-created PostgreSQL database, set `DATABASE_URL` and run `python CreateDB.py`. The script applies `DataBase.sql` and `INDEX.sql` in one transaction; `python CreateDB.py --dry-run` prints both files without connecting. The setup account needs permission to create extensions and roles. Install the Python dependency with `pip install psycopg2-binary`.

This is an initial bootstrap, not a repeatable migration. Use versioned Flyway migrations for existing databases. The Java application is configured for PostgreSQL, but database credentials and the database itself must still be provided.

The intended database name in the backend configuration is `confere_antes`. However, the current Spring Boot configuration still uses the MySQL JDBC URL and MySQL Connector/J. The application is not yet configured to connect to this PostgreSQL schema; its JDBC driver, connection URL, and dependency must be migrated before runtime integration.

Only the `User` table currently has a JPA entity in the backend. `transactions`, `scam_patterns`, `alerts`, `consents`, and `privacy_requests` are schema definitions without corresponding JPA entities.

The schema also defines `audit_log` and database functions for code verification, expiry, data export, and user anonymization. These functions are not yet integrated with Java services.

## PostgreSQL Features and Types

- `BIGINT GENERATED BY DEFAULT AS IDENTITY`: 64-bit numeric ID generated by PostgreSQL; suitable for the Java `Long` user ID.
- `UUID` with `gen_random_uuid()`: generated UUID identifiers. The script enables `pgcrypto` for UUID generation.
- `VARCHAR(n)`: bounded-length text; `TEXT`: unrestricted text.
- `NUMERIC(12,2)` and `NUMERIC(5,2)`: exact decimal values, suitable for currency and percentage-like scores.
- `TIMESTAMP`: date and time without time-zone information.
- `TIMESTAMPTZ`: an instant stored with time-zone-aware semantics.
- `TEXT[]`: PostgreSQL text array, used for pattern keywords.
- `JSONB`: PostgreSQL's binary JSON type, used for AI flags and indexed with GIN.
- `SMALLINT`: small integer, used for the verification-attempt counter.
- `BOOLEAN`: true/false value, used for account activation.

## Tables

### `users`

Stores account identity and account-state information.

| Field | PostgreSQL type | Rules and purpose |
|---|---|---|
| `id` | `BIGINT` identity | Primary key, generated by default. |
| `username` | `VARCHAR(50)` | Required and unique. |
| `email` | `VARCHAR(100)` | Required and unique. |
| `password_hash` | `VARCHAR(255)` | Required; stores a password hash, never a plaintext password. |
| `phone` | `VARCHAR(20)` | Optional phone number. |
| `created_at` | `TIMESTAMP` | Required; defaults to the current timestamp. |
| `updated_at` | `TIMESTAMP` | Optional; populated on updates by a trigger. |
| `active` | `BOOLEAN` | Required; defaults to `TRUE`. Can represent account deactivation if the application updates it. |

The current Java `User` entity maps `id`, `username`, `email`, `phone`, `password_hash`, `created_at`, and `active`. It does not currently map `updated_at`.

### `transactions`

Stores user-reported or system-tracked events that may need confirmation.

| Field | PostgreSQL type | Rules and purpose |
|---|---|---|
| `id` | `UUID` | Primary key; generated with `gen_random_uuid()`. |
| `user_id` | `BIGINT` | Required foreign key to `users.id`; currently uses `ON DELETE CASCADE`. |
| `type_transaction` | `VARCHAR(40)` | Required; limited to `cancelamento_boleto`, `correcao_compra`, `instalacao_app`, or `outro`. |
| `amount` | `NUMERIC(12,2)` | Optional; when present, must be non-negative. |
| `description_transaction` | `TEXT` | Optional system-generated description. |
| `description_client` | `TEXT` | Optional user-provided description. |
| `channel` | `VARCHAR(60)` | Optional; when present, limited to `ligacao`, `whatsapp`, `sms`, or `email`. |
| `status_transaction` | `VARCHAR(20)` | Required; defaults to `pending`; allowed values are `pending`, `confirmed`, `cancelled`, and `expired`. |
| `verification_code_hash` | `VARCHAR(256)` | Optional field intended for a non-plaintext verification-code digest. The application must implement the hashing/HMAC behavior; the column name alone does not provide protection. |
| `verification_code_expires_at` | `TIMESTAMPTZ` | Optional expiry instant; must be null or populated together with the verification-code hash. |
| `verification_attempts` | `SMALLINT` | Required; defaults to zero and is constrained to the range 0-5. |
| `created_at` | `TIMESTAMPTZ` | Required; defaults to the current instant. |
| `confirmed_at` | `TIMESTAMPTZ` | Optional; required when the status is `confirmed`, and must be null for other statuses. |

Indexes support lookup by `user_id` and lookup of pending transactions by status.

### `scam_patterns`

Stores reusable scam categories and their detection terms.

| Field | PostgreSQL type | Rules and purpose |
|---|---|---|
| `id` | `BIGINT` identity | Primary key, generated by default. |
| `category` | `VARCHAR(80)` | Required and unique category key. |
| `title` | `VARCHAR(150)` | Required display title. |
| `description` | `TEXT` | Required explanation of the pattern. |
| `keywords` | `TEXT[]` | Required text array; defaults to an empty array. |
| `created_at` | `TIMESTAMPTZ` | Required; defaults to the current instant. |

The current seed insert adds the `falso_funcionario_banco` pattern. Because `category` is unique and the insert has no conflict handling, running the script again can fail when that category already exists.

### `alerts`

Stores reported suspicious contacts and their analysis results.

| Field | PostgreSQL type | Rules and purpose |
|---|---|---|
| `id` | `UUID` | Primary key; generated with `gen_random_uuid()`. |
| `user_id` | `BIGINT` | Required foreign key to `users.id`; deletion is restricted while an alert references the user. |
| `transaction_id` | `UUID` | Optional foreign key to `transactions.id`; the default delete action prevents deleting a referenced transaction. |
| `pattern_id` | `BIGINT` | Optional foreign key to `scam_patterns.id`; the default delete action prevents deleting a referenced pattern. |
| `contact_channel` | `VARCHAR(20)` | Required; limited to `ligacao`, `whatsapp`, `sms`, or `email`. |
| `origin_number` | `VARCHAR(20)` | Required origin/contact number. |
| `description_alert` | `TEXT` | Required user-provided alert description. |
| `scam_category` | `VARCHAR(80)` | Optional category assigned by analysis. |
| `risk_level` | `VARCHAR(10)` | Optional; when present, limited to `low`, `medium`, or `high`. |
| `risk_score` | `NUMERIC(5,2)` | Optional score constrained to the range 0-100. |
| `ai_justification` | `TEXT` | Optional explanation from the analysis system. |
| `ai_flags` | `JSONB` | Required JSON value; defaults to an empty JSON array. A GIN index supports JSON queries. |
| `status_ia` | `VARCHAR(20)` | Required; defaults to `pending`; allowed values are `pending`, `evaluated`, and `evaluation_failure`. |
| `created_at` | `TIMESTAMPTZ` | Required; defaults to the current instant. |

Indexes support lookup by user, category, risk level, and JSON flags.

## Important Data Handling and Deletion Behavior

- Setting `users.active` to `FALSE` is a logical deactivation only if the application updates this field. It does not physically delete the user or related data. The current Java entity does not yet map this field.
- Deleting a user with `DELETE` cascades to that user's transactions because `transactions.user_id` uses `ON DELETE CASCADE`.
- Deleting a user is blocked while any alert references the user because `alerts.user_id` uses `ON DELETE RESTRICT`. Therefore, a user with alerts cannot currently be physically deleted; the deletion statement fails rather than deleting the alerts.
- Deleting a transaction referenced by an alert is blocked by the default foreign-key action on `alerts.transaction_id`.
- Deleting a scam pattern referenced by an alert is blocked by the default foreign-key action on `alerts.pattern_id`.
- These rules mean the current policy is mixed: transaction history cascades when possible, while alert history is retained and blocks deletion of its user. Confirm the intended retention/privacy policy before relying on physical deletion.
- Verification codes must not be stored in plaintext. `CreateCodeVerifyEntry.py` generates the code and HMAC-SHA256 digest using `VERIFICATION_PEPPER`, which stays outside the database. `verify_transaction_code` checks that the transaction belongs to the supplied user before counting attempts. The caller must pass the authenticated user's ID, never an ID supplied by the client.
- The application role has no direct `DELETE` permission. The privacy-officer function anonymizes a user and requires a BCrypt hash generated from a random discarded secret. The application rejects inactive users at login.

## Automatic Updates

The `users_set_updated_at` trigger runs before each update to a user and sets `updated_at` to the current time. The field is currently a timestamp without time zone, unlike the `TIMESTAMPTZ` fields in the other tables. Audit triggers cover `users`, `transactions`, `alerts`, `consents`, and `privacy_requests`. The audit actor is the authenticated PostgreSQL login (`session_user`); with a shared application login, it identifies the service account, not the end user.

## Current Integration Gaps

1. Configure `DB_URL`, `DB_USERNAME`, and `DB_PASSWORD`, and create the target database before starting the application.
2. Add JPA entities and mappings for `transactions`, `scam_patterns`, `alerts`, `consents`, and `privacy_requests` before expecting Java persistence for those tables.
3. Map `updated_at` if application features need to read or update it.
4. The seed insert is not idempotent; use a versioned migration or explicit conflict handling for repeatable initialization.
